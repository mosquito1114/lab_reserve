# lab_reserve 数据库表说明

> **面向对象**：项目协作者
> **数据库**：MySQL 8.0（`utf8mb4` / `utf8mb4_0900_ai_ci`）
> **建表脚本**：`backend/src/main/resources/db/migration/V1__init_schema.sql`（Flyway 管理，本文是它的说明文档）
> **表数量**：24 张，统一 `tb_` 前缀
> **演示数据**：`backend/src/main/resources/data/seed_data.sql`（服务启动时自动灌入）

---

## 阅读约定

### 1. 外键是「逻辑外键」

本项目**不使用数据库物理外键约束**（`information_schema` 里 `FOREIGN KEY` 数量为 0），
表间关系完全由**应用层（Service 层）保证**。

本文用 `→` 表示逻辑外键，例如 `role_id → tb_role.id`。

- **好处**：写入顺序灵活、批量导入方便、将来分库分表时不用先拆约束
- **代价**：数据库层挡不住脏数据，必须靠 Service 层的校验兜住

### 2. 反冗余原则：能联查就不存

凡是能通过 `JOIN` 得到的字段，**一律不落库**。所以全库没有姓名 / 编号 / 角色这类「快照字段」：

| 你要显示 | 怎么取 |
|---|---|
| 维修人姓名 | `JOIN tb_user ON id = maintainer_id` |
| 设备资源编号 | `JOIN tb_equipment ON id = equipment_id` |
| 预约时段 08:00–09:40 | `JOIN tb_time_slot ON id = slot_id` |
| 操作人姓名与角色 | `JOIN tb_user` / `JOIN tb_role ON id = user.role_id` |

唯一带「快照」字样的是 `before_json` / `after_json` —— 那是**变更内容本体**（没有它就无法知道改了什么），不是副本。

### 3. 删除策略

业务主体表（`tb_user` / `tb_laboratory` / `tb_equipment` / `tb_reservation`）**不物理删除**，
用 `status` 字段表达「注销 / 停用 / 已取消」。

## 一、用户权限模块（8 张）

### 1.1 `tb_user` —— 用户表（统一账号）

**存储所有用户的基本信息。** 五类角色共用这一张表，靠 `role_id` 区分。

| 关键字段 | 说明 |
|---|---|
| `username` / `password` | 登录凭据，密码为 BCrypt 哈希 |
| `real_name` | 真实姓名 |
| `role_id` | → `tb_role.id`，**角色划分的唯一依据** |
| `phone` | 手机号（明文存储，接口层脱敏输出） |
| `notify_email` | 是否开启邮件通知 0否 1是 |
| `status` | 1正常 / 0已注销 |

### 1.2 `tb_class` —— 班级表

存储班级信息。**它同时是学生「学院 / 专业」的唯一来源** —— `tb_student_info` 里没有 `college` / `major`，都从这里带出。

| 关键字段 | 说明 |
|---|---|
| `class_name` | 班级名，如 `软工2101`（全局唯一） |
| `college` / `major` | 所属学院 / 专业 |
| `grade` | 年级，如 `2021` |
| `student_count` | 班级人数（**教务上的班级规模**，不等于本系统里该班的账号数） |

**关联**：`tb_class` 1 ── N `tb_student_info`

### 1.3 `tb_student_info` —— 学生扩展表

存储学生的额外信息。

| 关键字段 | 说明 |
|---|---|
| `user_id` | → `tb_user.id`（唯一） |
| `student_no` | 学号（唯一） |
| `class_id` | → `tb_class.id`（学院 / 专业由班级带出） |

### 1.4 `tb_teacher_info` —— 教师扩展表

存储教师的额外信息。

| 关键字段 | 说明 |
|---|---|
| `user_id` | → `tb_user.id`（唯一） |
| `teacher_no` | 工号（唯一） |
| `college` | 所属学院 |
| `title` | 职称 |

### 1.5 `tb_staff_info` —— 管理类人员扩展表

存储**三类管理人员的公共信息**：系统管理员、实验室管理员、维修人员。
**这张表里没有「类型」字段** —— 类型由 `tb_user.role_id` 决定，避免双真相源。

| 关键字段 | 说明 |
|---|---|
| `user_id` | → `tb_user.id`（唯一） |
| `staff_no` | 工号（唯一） |
| `department` | 部门 |
| `maintainer_type` | 维修人员类别 1校内 / 2校外（**仅维修人员有值**） |

**区分三类人员**：

```sql
SELECT s.*, r.code AS role
FROM tb_staff_info s
JOIN tb_user u ON u.id = s.user_id
JOIN tb_role r ON r.id = u.role_id;   -- SYS_ADMIN / LAB_ADMIN / MAINTAINER
```

### 1.6 `tb_role` —— 角色表

五种角色的说明，**数据是写死的**（初始化脚本灌入，不在界面上增删）。

| `code` | 名称 | 说明 |
|---|---|---|
| `STUDENT` | 学生 | 预约设备、看实验课表、报修 |
| `TEACHER` | 教师 | 预约实验室（为班级排课）、预约设备 |
| `SYS_ADMIN` | 系统管理员 | 管用户与操作日志，**不能审批预约** |
| `LAB_ADMIN` | 实验室管理员 | 维护资源、审批预约、派单与验收 |
| `MAINTAINER` | 维修人员 | 接收派单并更新维修进度 |

### 1.7 `tb_permission` —— 权限表

存储系统各模块的具体权限点，如「查询用户列表」「审批预约」。
`code` 命名规范为 `模块:资源:动作`，例如 `resource:lab:create`、`reservation:audit`。

### 1.8 `tb_role_permission` —— 角色权限中间表

角色与权限是**多对多**关系，所以需要这张中间表。

**关联**：`tb_role` N ── N `tb_permission`（经 `tb_role_permission`）

## 二、实验室资源模块（3 张）

### 2.1 `tb_experiment_type` —— 实验类型字典

存储所有实验类型：演示性 / 验证性 / 综合性 / 设计性 / 创新性。

### 2.2 `tb_laboratory` —— 实验室表

存储所有实验室。

| 关键字段 | 说明 |
|---|---|
| `lab_no` | 实验室编号 `LAB-XX`（唯一） |
| `location` | 位置 |
| `open_time_start` / `open_time_end` | 开放时间 |
| `open_weekdays` | 开放星期，如 `1,2,3,4,5` |
| `capacity` | 容纳人数 |
| `experiment_type_id` | → `tb_experiment_type.id`，**一个实验室只开展一种固定类型** |

### 2.3 `tb_equipment` —— 设备表

存储所有设备。

| 关键字段 | 说明 |
|---|---|
| `resource_no` | 资源编号 `ZY-XX-YYY`（唯一），`XX` = 所属实验室序号 |
| `model` | 型号 |
| `stock` | 库存数量（支持一台设备被多人同时借用） |
| `status` | 1正常 / 2维修中 / 3报废 / 0停用 |
| `lab_id` | → `tb_laboratory.id` |
| `next_calibration_date` | 下次校准日期（手工填写，系统不推算、不提醒） |

**本模块的关系**：

```
tb_experiment_type 1 ── N tb_laboratory        一个实验类型对应多个实验室
tb_laboratory      1 ── N tb_equipment         一个实验室包含多个设备
```

> 资源的变更留痕（谁在什么时候因为什么改了资源）记在 `tb_resource_update_log`，见第六节。

## 三、预约与排队模块（7 张）

### 3.1 `tb_time_slot` —— 固定时段字典

存储预约时段：`1-2节 08:00-09:40`、`3-4节 10:00-11:40`、`5-6节 14:00-15:40` 等。

**预约按 `slot_id` 占用，一个时段一条预约** —— 这是「时段独占」的基础。

### 3.2 `tb_reservation` —— 预约申请表

**存储两类预约**：

| `resource_type` | 场景 | 主资源字段 |
|---|---|---|
| `1` 实验室 | **仅教师**可以提交（为班级排课） | `lab_id` |
| `2` 设备 | 学生和教师都可以提交 | `equipment_id` + `equipment_count` |

| 关键字段 | 说明 |
|---|---|
| `reserve_no` | 预约号 `R-YYYYMMDD-XXXX`（唯一） |
| `applicant_id` | → `tb_user.id`，申请人 |
| `reserve_date` / `slot_id` | 预约日期 + 时段 |
| `use_people` | 使用人数 |
| `experiment_type_id` | → `tb_experiment_type.id`，**必须等于实验室的可开展类型** |
| `course_name` | 授课课程（教师预约实验室时必填） |
| `status` | `PENDING` `APPROVED` `REJECTED` `CANCELED` `CHANGE_PENDING` `EXPIRED` |
| `from_queue` / `source_queue_id` | 是否由排队转正 / 来源排队记录 |
| `occupy_key` | **生成列**，实验室时段占用唯一键（并发兜底，见下文） |

> `status ∈ {PENDING, APPROVED, CHANGE_PENDING}` 视为**占用资源**。待审核也占位，避免两人同抢一个时段后管理员批了第二个。

### 3.3 `tb_reservation_class` —— 预约上课班级中间表

**预约与班级的多对多关系**：教师预约实验室时必须指定上课班级（至少一个），
一次课可以带多个班。

**这张表是学生端「我的实验课表」的唯一数据来源**：

```sql
SELECT r.*, l.lab_no, l.name
FROM tb_reservation r
JOIN tb_reservation_class rc ON rc.reservation_id = r.id
JOIN tb_laboratory l ON l.id = r.lab_id
WHERE rc.class_id = {当前学生的班级} AND r.status = 'APPROVED';
```

### 3.4 `tb_reservation_equipment` —— 实验室预约附带的设备清单

⚠️ **这张表只在「实验室预约（`resource_type=1`）附带设备」时使用**。

设备预约（`resource_type=2`）的**主资源**直接存在 `tb_reservation.equipment_id`，**不走这张表**。
这样设计是为了支持需求里的「调整申请 → 增加设备」。

**关联**：`tb_reservation` N ── N `tb_equipment`

### 3.5 `tb_reservation_change_request` —— 预约调整申请

记录教师 / 学生发起的「修改时间 / 增减设备 / 取消预约」申请。

**核心机制**：申请期间 `tb_reservation` 的业务字段**一个字都不动**，只把 `status` 改成 `CHANGE_PENDING`；
管理员审批通过后，才把 `after_json` 回写到预约单。

| 关键字段 | 说明 |
|---|---|
| `change_type` | 1修改 / 2取消 |
| `before_json` / `after_json` | 变更前 / 变更后的完整快照（**变更内容本体**） |
| `reason` | 申请原因 |
| `status` | 0待审批 / 1通过 / 2驳回 |

**发起条件**：距实验开始 **≥ 24 小时**。

### 3.6 `tb_resource_queue` —— 资源排队队列

当目标时段被占时，师生可以「加入排队」，按**申请时间先后**排序。

| 关键字段 | 说明 |
|---|---|
| `queue_no` | 排队号 `P-资源编号-YYYYMMDD-序号`（唯一） |
| `resource_type` / `lab_id` / `equipment_id` | 排的是哪个资源 |
| `reserve_date` / `slot_id` | 排的是哪个时段 |
| `status` | `QUEUING` `NOTIFIED` `CONFIRMED` `ABANDONED` `TIMEOUT` `CANCELED` |
| `join_time` | 入队时间（排序依据） |

**唯一约束**：`uk_queue_user_slot` —— 同一用户对同一资源同一时段**只能排一次**。

> 队列真相源在 Redis ZSet（`lab:reserve:queue:{type}:{resId}:{date}:{slotId}`），
> 本表负责持久化与业务字段承载，**排队顺位不落库**。

### 3.7 `tb_queue_ban_record` —— 排队禁入记录（7 天）

**候补放弃或超时**的用户，7 天内不得再加入**同一资源**的排队队列。

| 关键字段 | 说明 |
|---|---|
| `user_id` | 被禁入用户 |
| `resource_type` / `lab_id` / `equipment_id` | 禁入的资源（按资源维度禁入） |
| `reason` | 禁入原因 |
| `start_time` / `end_time` | 默认 `end_time = start_time + 7 天` |

**本模块的关系**：

```
tb_user        1 ── N tb_reservation              申请人
tb_laboratory  1 ── N tb_reservation              仅 resource_type=1
tb_equipment   1 ── N tb_reservation              仅 resource_type=2（主资源）
tb_time_slot   1 ── N tb_reservation
tb_reservation N ── N tb_class                    经 tb_reservation_class
tb_reservation N ── N tb_equipment                经 tb_reservation_equipment
tb_reservation 1 ── N tb_reservation_change_request
tb_user        1 ── N tb_resource_queue / tb_queue_ban_record
```

## 四、设备维修模块（2 张）

### 4.1 `tb_repair_order` —— 设备报修工单

师生发现设备异常时提交的工单，走完整流程：**报修 → 复核 → 派单 → 维修 → 验收 → 归档**。

| 关键字段 | 说明 |
|---|---|
| `order_no` | 工单号 `WX-YYYYMMDD-XXXX`（唯一） |
| `submitter_id` | → `tb_user.id`，报修人 |
| `equipment_id` | → `tb_equipment.id`，报修设备 |
| `fault_desc` / `fault_scene` | 故障现象 / 发生场景 |
| `fault_images` | 故障截图 URL（阿里云 OSS），逗号分隔 |
| `priority` | 1低 2中 3高 4紧急 |
| `status` | `SUBMITTED` `REJECTED` `ASSIGNED` `REPAIRING` `REPAIRED` `ACCEPTED` `REOPENED` |
| `reviewer_id` / `assignee_id` / `accept_user_id` | → `tb_user.id`，复核人 / 派单人 / 验收人 |
| `archive_time` | **归档时间**（验收通过时写入） |

> **同一条工单上有 4 个用户引用**：报修人、复核人、维修人、验收人。

### 4.2 `tb_repair_record` —— 维修进度记录表

**维修人员每次更新进度就追加一条**，所以一条工单对应多条记录。

| 关键字段 | 说明 |
|---|---|
| `order_id` | → `tb_repair_order.id` |
| `maintainer_id` | → `tb_user.id`，维修人 |
| `status` | 1维修中 / 2已完成 |
| `repair_desc` | 维修说明（完成后必填） |
| `parts_replaced` | 配件更换记录 |

> **注意**：**归档不在本表**。归档由 `tb_repair_order.archive_time` + `status='ACCEPTED'` 承载。

**本模块的关系**：

```
tb_equipment    1 ── N tb_repair_order
tb_repair_order 1 ── N tb_repair_record
tb_user         1 ── N tb_repair_order     （submitter_id / reviewer_id / assignee_id / accept_user_id）
tb_user         1 ── N tb_repair_record    （maintainer_id）
```

## 五、消息通知模块（1 张）

### 5.1 `tb_message` —— 消息表

**站内信本体 + 邮件投递终态**，一张表解决两件事。**邮件正文不单独落库**，由本表正文渲染。

| 关键字段 | 说明 |
|---|---|
| `receiver_id` | → `tb_user.id`，接收人 |
| `type` | `RESERVATION_AUDIT` / `QUEUE_POSITION` / `CANDIDATE_NOTICE` / `REPAIR` / `CHANGE_AUDIT` / `SYSTEM` |
| `title` / `content` | 正文（也是渲染邮件的唯一来源） |
| `biz_type` / `biz_id` | 关联业务（预约单 / 排队记录 / 工单） |
| `email_required` | 是否需要邮件投递 |
| `email_state` | NULL未发/投递中 / OK成功 / DEAD死信 |
| `email_last_error` | 最后一次失败原因 |
| `is_read` / `is_deleted` | 已读 / 用户视角删除（不物理删） |

> **邮件重试的全过程在 Redis Stream 里**（`msg:email` / `msg:email:dead`），
> 本表只在**最终成功或进死信时回写一次** `email_state`，重试期间不写库。

## 六、日志审计模块（3 张）

### 6.1 `tb_operation_log` —— 操作日志表

**记录所有角色的关键操作**（不只是实验室管理员），用于追溯异常 / 恶意操作。
**只增不改不删**。

| 关键字段 | 说明 |
|---|---|
| `operator_id` | → `tb_user.id`，操作人（登录失败时为空） |
| `module` | `auth` / `user` / `resource` / `reservation` / `queue` / `repair` / `message` / `statistics` / `system` |
| `operation_type` | `LOGIN` `LOGOUT` `CREATE` `UPDATE` `DELETE` `AUDIT` `EXPORT` `ASSIGN` `ACCEPT` `QUERY_PHONE` |
| `content` | 操作内容描述 |
| `request_method` / `request_url` / `request_param` | 请求信息，参数**已脱敏** |
| `ip` / `user_agent` | 客户端信息 |
| `result` / `error_msg` / `cost_ms` | 成功失败 / 错误信息 / 耗时 |

> 操作人姓名与角色**不落库**，查询时 `JOIN tb_user` / `JOIN tb_role`。

### 6.2 `tb_candidate_notice_log` —— 候补通知日志

记录**每一次候补通知**：什么时候通知了谁、给了多长确认时间、对方怎么响应。

| 关键字段 | 说明 |
|---|---|
| `queue_id` | → `tb_resource_queue.id` |
| `notice_time` / `deadline` | 通知时间 / 确认截止时间（默认 +30 分钟） |
| `channel` | 1站内信 / 2邮件 |
| `action` | 0未响应 / 1确认 / 2放弃 / 3超时 |
| `seq` | 第几次被通知（顺延后会再次轮到同一人，`seq` 递增） |

### 6.3 `tb_resource_update_log` —— 资源更新日志

**实验室 / 设备的每一次写操作都留痕**，含变更前后快照与**更新原因**。

| 关键字段 | 说明 |
|---|---|
| `resource_type` / `resource_id` | 1实验室 / 2设备（多态引用） |
| `operation` | 1新增 / 2修改 / 3删除·停用 |
| `before_json` / `after_json` | 变更前 / 变更后快照 |
| `update_reason` | **更新原因（强制填写）** |
| `operator_id` | → `tb_user.id` |

## 附录 A：关键业务规则

| 规则 | 说明 |
|---|---|
| **时段独占** | 同一实验室 + 同一日期 + 同一时段，只能有一条**占用中**的预约 |
| **占用集合** | `status ∈ {PENDING, APPROVED, CHANGE_PENDING}` 都算占用 |
| **实验室仅教师可约** | 学生提交实验室预约 → `409 LAB_RESERVE_TEACHER_ONLY` |
| **上课班级必填** | 教师预约实验室必须指定至少一个班级 → 否则 `409 CLASS_REQUIRED` |
| **实验类型必须匹配** | 预约的 `experiment_type_id` 必须等于实验室的 `experiment_type_id` |
| **设备按库存** | `Σ已占数量 < stock` 才能预约，多人可同时借用 |
| **调整申请窗口** | 距实验开始 ≥ 24 小时；审批通过前不动业务字段 |
| **候补确认时限** | 30 分钟（可配置），超时自动顺延给下一位 |
| **7 天禁入** | 候补放弃 / 超时后，7 天内不得再加入**同一资源**的排队 |

### 并发兜底：`tb_reservation.occupy_key`

实验室时段的最终防线是一个**生成列 + 唯一索引**：

```sql
occupy_key VARCHAR(80) GENERATED ALWAYS AS (
    IF(status IN ('PENDING','APPROVED','CHANGE_PENDING') AND resource_type = 1,
       CONCAT(lab_id, '-', reserve_date, '-', slot_id), NULL)
) STORED,
UNIQUE KEY uk_reservation_lab_occupy (occupy_key)
```

只有「占用中」的状态才生成键值，其余为 `NULL`（MySQL 唯一索引允许多个 `NULL`）。
分布式锁没拦住时，靠它把数据库异常翻译成 409。

## 附录 B：Redis 与数据库的分工

| 数据 | 存在哪 | 原因 |
|---|---|---|
| 排队队列与顺位 | **Redis ZSet**（真相源） | 顺位要实时算，`ZRANK` 比 SQL 排序快得多 |
| 排队记录的业务字段 | MySQL `tb_resource_queue` | 持久化、可查询 |
| 候补超时扫描 | Redis ZSet（score = deadline） | 定时任务按时间范围取，不用扫全表 |
| 收件箱排序与未读数 | Redis ZSet + String | 不过期，容量可控 |
| 邮件重试状态 | Redis Stream（PEL + 死信） | 重试过程不写库，避免写放大 |
| 消息正文与邮件终态 | MySQL `tb_message` | 需要可 SQL 查询的台账 |

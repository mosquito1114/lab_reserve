# 02 · 数据库设计说明书

> 项目：**lab_reserve · 实验室预约管理系统**
> 版本：v1.0 ｜ 最后更新：2026-10-24
> 建表脚本：`backend/src/main/resources/db/migration/V1__init_schema.sql`（Flyway 管理）；
> 面向协作者的逐表速查：`instructs/数据库表说明.md`。

---

## 1. 总体约定

| 项 | 约定 |
|---|---|
| 库名 | `lab_reserve`（utf8mb4 / InnoDB） |
| 表前缀 | 业务表 `tb_`，共 **24 张**；RAG 模块另有 6 张 `tb_rag_*`（独立模块，见 `docs/rag-design.md`） |
| 主键 | `BIGINT AUTO_INCREMENT`，实体用 `IdType.AUTO` |
| 外键 | **逻辑外键**（不建物理 FOREIGN KEY），关联字段名与含义写注释 |
| 反冗余 | 能 JOIN 得到的就不落库（如学生只存 `class_id`，学院/专业由班级带出） |
| 时间 | `created_at` / `updated_at` 由列默认值维护（`DEFAULT CURRENT_TIMESTAMP`），不用 MetaObjectHandler |
| 删除 | 业务主体不物理删除：用户/实验室/设备用 `status`，预约用状态流转；操作日志只增不改不删 |
| 迁移 | 版本号只增不改；已执行过的脚本一律不动，新增结构写 V12+ |

## 3. 关键表说明

### 3.1 `tb_user` 统一账号

五类角色共用一张表，靠 `role_id` 区分。

| 字段 | 说明 |
|---|---|
| `username` / `password` | 登录凭据；密码 BCrypt（`$2a$` 前缀）；`uk_username` |
| `real_name` / `role_id` / `status` | 姓名、角色、1 正常 / 0 已注销 |
| `phone` / `email` | 手机号明文存储、接口层脱敏；邮箱用于邮件通知 |
| `notify_email` | 0 关闭（默认）/ 1 开启 |
| `last_login_at` | 最近登录时间（登录成功时更新） |

> 学生/教师/维修人员的业务档案分别在 `tb_student_info`（`student_no` + `class_id`）、
> `tb_teacher_info`（`teacher_no` + `college` + `title`）、`tb_staff_info`（`staff_no` + `maintainer_type`）。

### 3.2 `tb_reservation` 预约申请（核心）

| 字段 | 说明 |
|---|---|
| `reserve_no` | 预约号 `R-YYYYMMDD-XXXX`（Redis 按天自增），`uk_reservation_no` |
| `applicant_id` / `resource_type` | 申请人、1 实验室 / 2 设备 |
| `lab_id` / `equipment_id` / `equipment_count` | 主资源；设备预约时 `equipment_count` 参与库存计算 |
| `reserve_date` / `slot_id` | 预约日期与时段（时段是全校统一字典） |
| `experiment_type_id` / `course_name` / `purpose` | 实验类型、授课课程（教师必填）、实验内容 |
| `status` | `PENDING / APPROVED / REJECTED / CANCELED / CHANGE_PENDING / EXPIRED` |
| `from_queue` / `source_queue_id` | 是否候补转正、来源排队记录 |
| **`occupy_key`（生成列）** | `IF(status IN ('PENDING','APPROVED','CHANGE_PENDING') AND resource_type=1, CONCAT(lab_id,'-',reserve_date,'-',slot_id), NULL)`，配 `uk_reservation_lab_occupy` 做并发兜底；非占用状态为 NULL（MySQL 唯一索引允许多个 NULL） |

**占用集合** = `{PENDING, APPROVED, CHANGE_PENDING}`：冲突判定、库存计算、可用时段都按它。

### 3.3 `tb_reservation_class` / `tb_reservation_equipment`

- `tb_reservation_class`：教师预约实验室时指定上课班级，`uk_res_class(reservation_id, class_id)`；
  **学生「我的实验课表」的数据来源**（按 `class_id` 反查 `APPROVED` 的预约）。
- `tb_reservation_equipment`：实验室顺带借的设备清单，调整申请的「增减设备」也落这张表。

### 3.4 `tb_reservation_change_request` 调整申请

| 字段 | 说明 |
|---|---|
| `change_type` | 1 修改 / 2 取消 |
| `before_json` / `after_json` | 变更前 / 变更后快照（只放业务字段） |
| `status` | 0 待审批 / 1 通过 / 2 驳回 |
| 约定 | **审批通过前 `tb_reservation` 的业务字段一律不改**，只把状态置 `CHANGE_PENDING` |

### 3.5 `tb_resource_queue` 排队记录

| 字段 | 说明 |
|---|---|
| `queue_no` | 排队号 `P-资源编号-YYYYMMDD-序号`，`uk_queue_no` |
| `status` | `QUEUING / NOTIFIED / CONFIRMED / ABANDONED / TIMEOUT / CANCELED` |
| `join_time` | 入队时间（与 Redis ZSet 的 score 一致） |
| `uk_queue_user_slot` | 同一用户 + 资源 + 日期 + 时段只能有一条 |

> **顺位不落库**：队列顺序只在 Redis ZSet（`lab:reserve:queue:{type}:{resId}:{date}:{slotId}`，member=userId），
> DB 只承载状态机与业务字段。

### 3.6 `tb_candidate_notice_log` / `tb_queue_ban_record`

- 通知记录：`deadline`（默认 now+30min）、`action`（0 未响应 / 1 确认 / 2 放弃 / 3 超时）、`seq`；
  一条 `action=0` 的记录就是「正在等这个人确认」，也是顺延的幂等依据。
- 禁入记录：`user_id + resource_type + lab_id/equipment_id + start_time/end_time`（默认 7 天）。

### 3.7 `tb_repair_order` / `tb_repair_record`

工单：`order_no`（`WX-YYYYMMDD-XXXX`）、`equipment_id`、`fault_desc/fault_scene/fault_images`（OSS URL 逗号分隔）、
`priority`（1 低 – 4 紧急）、`status`（7 态）、复核/派单/验收/归档时间。
验收字段内联在工单表（验收只发生一次），维修过程写 `tb_repair_record`（1 维修中 / 2 已完成）。

### 3.8 `tb_message` 消息（站内信 + 邮件终态）

| 字段 | 说明 |
|---|---|
| `type` | `RESERVATION_AUDIT / QUEUE_POSITION / CANDIDATE_NOTICE / REPAIR / CHANGE_AUDIT / SYSTEM` |
| `email_required` / `email_state` / `email_last_error` | 邮件是否需要、状态（NULL 未入队 / SENDING / OK / DEAD）、失败原因 |
| `is_read` / `is_deleted` | 已读、用户视角删除（30 天后由定时任务物理清理） |

> 收件箱顺序在 Redis ZSet `lab:reserve:inbox:{userId}`，未读数在 `lab:reserve:inbox:unread:{userId}`；
> 未读数缺失时按库重建，另有每小时校正任务。

### 3.9 `tb_resource_update_log` 资源变更留痕

`resource_type`（1 实验室 / 2 设备）+ `resource_id`、`operation`（1 新增 / 2 修改 / 3 状态变更）、
`before_json` / `after_json`（只放业务字段，时间统一 `HH:mm` 字符串）、`update_reason`（强制）、`operator_id`。

### 3.10 `tb_operation_log` 操作日志

`module` + `operation_type`（LOGIN / CREATE / UPDATE / DELETE / AUDIT / EXPORT / ASSIGN / ACCEPT / QUERY_PHONE …）、
`content`、`request_url`、`request_param`（脱敏后截断）、`ip`、`user_agent`、`result`、`cost_ms`。
只增不改不删，异步写入；支持按模块/类型/操作人/时间筛选与 Excel 导出。

## 4. 索引与约束（支撑高频场景）

| 表 | 索引 | 场景 |
|---|---|---|
| `tb_user` | `uk_username`、`idx_role` | 登录、按角色筛用户 |
| `tb_reservation` | `uk_reservation_no`、`uk_reservation_lab_occupy`、`idx_lab_slot`、`idx_equip_slot`、`idx_status`、`idx_date` | **判冲查询**、审核列表、统计区间 |
| `tb_resource_queue` | `uk_queue_no`、`uk_queue_user_slot`、`idx_lab_slot`、`idx_equip_slot` | 重复入队拦截、整条队列查询 |
| `tb_candidate_notice_log` | `idx_queue`、`idx_deadline(action)` | 超时扫描 |
| `tb_queue_ban_record` | `idx_user_resource` | 入队前禁入判断 |
| `tb_message` | `idx_receiver`、`idx_unread`、`idx_email_state` | 收件箱、未读数、邮件对账 |
| `tb_operation_log` | `idx_created`、`idx_type`、`idx_operator` | 日志筛选 |
| `tb_resource_update_log` | `idx_resource`、`idx_created` | 资源变更追溯 |

**生成列唯一索引是并发正确性的最后一道门**：即使分布式锁失效（租约到期/多实例漏锁），
数据库也会拒绝第二条同实验室同时段的占用记录，服务层把异常翻译成 409。

## 5. Redis 数据（与 DB 的分工）

| Key | 类型 | 用途 | TTL |
|---|---|---|---|
| `perm:role:{roleId}` | STRING | 角色权限码缓存 | 不设，改权限后主动 DEL |
| `lock:reserve:*` / `lock:queue:*` / `lock:job:*` | RLock | 判冲、队列、定时任务互斥 | 租约到期释放 |
| `queue:{type}:{resId}:{date}:{slotId}` | ZSET | 排队队列（member=userId, score=入队时间） | 不设 |
| `queue:notice:deadline` | ZSET | 候补超时扫描（member=queueId, score=deadline） | 不设 |
| `inbox:{userId}` / `inbox:unread:{userId}` | ZSET / STRING | 收件箱索引 / 未读数 | 不设 |
| `stream:msg:email` / `:dead` | STREAM | 邮件投递 / 死信（消费组 `mailer`） | MAXLEN ~ 10000 / 不设 |
| `seq:reservation:{yyyyMMdd}` / `seq:repair:{yyyyMMdd}` / `queue:seq:*` | STRING | 单号自增 | 48h |
| `stat:occupancy:{begin}:{end}` | STRING | 占用率聚合缓存 | 10min |

> 由于队列/收件箱/未读数是**业务数据而非缓存**，Redis 必须配置 `maxmemory-policy noeviction`。

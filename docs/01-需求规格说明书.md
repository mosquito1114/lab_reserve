# 01 · 需求规格说明书

> 项目：**lab_reserve · 实验室预约管理系统**（课程设计）
> 版本：v1.0 ｜ 最后更新：2026-10-24
> 说明：本文是交付版需求说明，内容与当前实现一致；过程中的问答记录见开发协作稿（`agents/req.md`）。

---

## 1. 项目背景与目标

高校实验室/设备的借用目前多靠线下登记：教师排课要逐个实验室问、学生借设备靠口头约定，
容易出现「同一时段被两个人占」「设备坏了没人跟」「谁借走了不知道」三类问题。

本系统把这三件事线上化：

| 目标 | 落地方式 |
|---|---|
| 时段不冲突 | 实验室时段独占（分布式锁 + 数据库唯一索引兜底） |
| 抢不到有秩序 | Redis ZSet 排队 + 候补通知 + 超时顺延 + 7 天禁入 |
| 坏了有人管 | 报修 → 复核 → 派单 → 维修 → 验收 的工单闭环 |
| 过程可追溯 | 操作日志（只增不改）+ 资源变更留痕（before/after 快照） |

## 2. 角色与职责

| 角色 | 编码 | 能做什么 |
|---|---|---|
| 学生 | `STUDENT` | 预约**设备**、报修、排队、查看「我的实验课表」（教师为自己班级排的实验课） |
| 教师 | `TEACHER` | 上述全部 + **预约实验室并指定上课班级**（教学实验室只由教师排课） |
| 实验室管理员 | `LAB_ADMIN` | 资源维护（实验室/设备/字典）、预约与调整审批、排队调度、报修复核/派单/验收 |
| 维修人员 | `MAINTAINER` | 只处理**指派给自己**的工单：更新进度、完成维修 |
| 系统管理员 | `SYS_ADMIN` | 用户/班级/角色权限/操作日志/系统运行状态，以及全部统计报表 |

> **权限是数据**：`tb_role_permission` 决定接口与菜单，同一个权限码既控制按钮也控制接口，界面可勾选调整。

## 3. 功能模块

### 3.1 认证与权限

- JWT（Access + Refresh），登出/改密后 Access 进 Redis 黑名单；
- 登录失败 5 次锁定 15 分钟；
- 权限码缓存 `lab:reserve:perm:role:{roleId}`，改权限后主动失效；
- 菜单由后端按权限过滤后下发（前端只渲染，不判断）。

### 3.2 用户与班级

- 五类角色共用 `tb_user`，学生档案只存 `studentNo + classId`（学院/专业由班级带出）；
- 角色、账号、学号工号**不可修改**，换角色需注销后重建；
- 手机号明文存储、接口层脱敏；本人看自己为明文；
  管理员查看完整手机号需 `revealPhone=true` + `user:view-phone`，并写 `QUERY_PHONE` 日志；
- 注销 = `status=0`（不物理删除，历史记录继续可引用）。

### 3.3 资源管理

- 实验室：编号 `LAB-XX`、开放星期、开放时间窗、容量、可开展实验类型（一个实验室一种类型）；
- 设备：编号 `ZY-XX-YYY`、库存、状态（正常/维修中/报废/停用）、所属实验室；
- 字典：实验类型、固定时段（全校统一）；
- **变更必须留痕**：`create/update/update_status` 强制 `updateReason`，写 before/after 快照；
- 字典被实验室/预约引用时禁止删除（409），引导改为停用；
- 可用时段：按「停用 → 日期已过 → 非开放星期 → 不在开放时间 → 已被预约」逐条给原因，
  并同时返回排队人数与我的顺位。

### 3.4 预约与调整（核心）

**谁能约什么**

| 资源 | 谁能预约 | 说明 |
|---|---|---|
| 实验室 | 仅 `TEACHER` | 必须带上课班级（至少 1 个）与实验类型（必须等于实验室类型） |
| 设备 | `STUDENT` + `TEACHER` | 库存制，多人可同时借用，`Σ已借 ≤ 库存` |

**状态机**

```
PENDING ──审核通过──> APPROVED ──到期未使用──> EXPIRED
   │                     │
   ├──审核驳回──> REJECTED├──管理员释放──> CANCELED
   └──本人撤销──> CANCELED└──调整审批中──> CHANGE_PENDING ──通过/驳回──> 回写/回 APPROVED
```

> 占用集合 = `{PENDING, APPROVED, CHANGE_PENDING}`，冲突判定与库存计算都按它。

**调整申请的两条硬规则**

1. 同一预约同时只允许一条待审申请；发起窗口为「距开始 ≥ 24 小时」（按 `日期 + 时段开始时间` 计算）；
2. **审批通过前，预约单的业务字段一个都不改**，只把 `status` 置 `CHANGE_PENDING`；
   变更内容存在 `before_json` / `after_json`，审批通过时才回写。

### 3.5 排队与候补

```
QUEUING ──时段空出──> NOTIFIED ──确认──> CONFIRMED（直接生成 APPROVED 预约单）
   │                     ├──放弃──> ABANDONED（写 7 天禁入）
   └──本人取消──> CANCELED └──超时──> TIMEOUT（写 7 天禁入）
```

- 入队前置：实验室只能教师排、时段已满、未处于禁入期、未重复入队；
- 顺位 = Redis ZSet 的 `ZRANK + 1`，**实时计算、不落库**；
- 顺延来源统一：管理员释放、预约取消、调整审批通过、队首超时/放弃；
- 候补确认时限默认 **30 分钟**，超时自动顺延下一位；放弃/超时禁入 **7 天**（取消排队不禁入）。

### 3.6 消息通知

- 业务代码统一调 `MessageService.send(...)`（站内信 + 收件箱索引 + 未读数 + 邮件入队一次完成）；
- 邮件走 Redis Stream：失败不 ACK → 定时重投 → 达到 `max-retry`（默认 3 次总投递）进死信；
- 状态机：`NULL 未入队 → SENDING 投递中 → OK / DEAD`；
- 收件箱：Redis ZSet 索引 + DB 正文；未读数缺失时按库重建，每小时校正一次。

### 3.7 设备运维

```
SUBMITTED ──复核确认──> ASSIGNED ──更新进度──> REPAIRING ──完成──> REPAIRED ──验收通过──> ACCEPTED
     │                      ↑                                        │
     └──复核驳回──> REJECTED └──────── 验收不通过 → REOPENED ─────────┘
```

- 派单只能给 `MAINTAINER` 且账号正常；
- 维修人只能操作**指派给自己**的工单；
- 验收通过：写 `archive_time` + 设备状态恢复「正常」；不通过：`REOPENED` 可继续维修；
- **设备维修不联动作废任何预约**。

### 3.8 统计报表

7 个接口：总览、资源占用率、实验类型占比、预约成功率、资源预约占比、预约趋势（日/周/月）、Excel 导出（5 种）。
占用率口径 = 已占用时段 / 开放时段（实验室按开放星期与时间窗计算；设备再乘库存）。
导出与页面共用同一份聚合，保证「页面数字 = Excel 数字」。

## 4. 业务规则汇总（必须实现）

| # | 规则 |
|---|---|
| R1 | 实验室时段独占：同一实验室 + 日期 + 时段只允许一条占用中的预约 |
| R2 | 设备库存：`Σ equipment_count ≤ stock`，附带设备一并计入 |
| R3 | 实验室只有教师能约，且必须带上课班级、实验类型必须匹配 |
| R4 | 学生「我的实验课表」= 按自己班级反查 `tb_reservation_class` 且状态 `APPROVED` |
| R5 | 调整申请需提前 24h；通过前不改业务字段 |
| R6 | 候补超时/放弃写 7 天禁入；取消排队不写 |
| R7 | 资源变更强制填更新原因；字典被引用禁止删除 |
| R8 | 手机号默认脱敏；查看完整手机号必须留痕 |
| R9 | 不存身份证号（任何表、日志、导入文件都不允许出现） |
| R10 | 业务主体不物理删除（用户/实验室/设备用 `status`，预约用状态流转） |
| R11 | 设备维修不影响已生效的预约 |
| R12 | 操作日志只增不改不删，异步写入 |

## 5. 并发控制（课程要求 K10）

| # | 场景 | 手段 |
|---|---|---|
| 1 | 预约提交（同实验室同时段） | Redisson 锁 `lock:reserve:{type}:{resId}:{date}:{slotId}` + `tb_reservation.uk_reservation_lab_occupy`（`occupy_key` 生成列唯一索引）兜底 |
| 2 | 审核通过 | 同一把锁内**二次判冲**（排除自身） |
| 3 | 加队列 / 取消队列 | 锁 `lock:queue:...` + `ZADD NX` + `uk_queue_user_slot` |
| 4 | 候补确认 / 超时 / 放弃 | 通知记录 CAS（0→1/2/3）+ 排队状态 CAS（`NOTIFIED→…`）+ 锁内再确认时段空闲 |
| 5 | 预约号 / 排队号生成 | Redis `INCR`（按天，48h 过期） |
| 6 | 邮件投递 | Redis Stream 消费组（天然单实例消费）+ PEL 重投 |

> 并发验收：`scripts/stress/reservation_concurrency.py` 对同一时段 **50 并发**，
> 结果必须是「恰好 1 条成功、其余 409」，数据库中该时段只有 1 条占用中的预约。

## 6. 非功能要求

| 项 | 要求 |
|---|---|
| 接口风格 | 全部 `POST` + JSON body（唯一例外 `/api/file/upload` 用 multipart） |
| 响应格式 | 统一 `Result<T>`；HTTP 状态码 == 响应体 `code`；业务冲突 409 |
| 分页 | 请求体继承 `PageQuery`，响应 `PageResult<T>`，`pageSize ≤ 100` |
| 安全 | 密码 BCrypt；凭据只在 `.env`；所有写操作打 `@OpLog` |
| 可运维 | `./dev.sh start/stop/restart/status/logs`；Docker Compose 一键部署 |
| 可验收 | 每轮迭代提供可重复执行的验收脚本（`scripts/acceptance/*.py`） |

## 8. 验收标准（整体）

- 6 个业务模块的接口与页面全部可用，权限矩阵与第 2 节一致；
- 迭代验收脚本全绿：`iter1_auth` 62、`iter2_user` 48、`iter3_message` 55+3skip、
  `iter4_resource` 62、`iter5_reservation` 47、`iter6_queue` 37、`iter7_repair` 42、`iter8_statistics` 35；
- 50 并发压测满足「恰好 1 条成功」；
- 全新环境 `docker compose down -v && ./dev.sh start` 后所有功能可用；
- 后端 `./mvnw test` 与前端 `npm run build` 均通过。
